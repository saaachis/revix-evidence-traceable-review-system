Section 1, continued

Structure that a build can enforce

The one rule that holds it together

Dependencies run in one direction only. The API and the pipeline both depend on revix_core; core depends on neither, so the read path and the write path cannot tangle.

Enforced by import linting in CI, not by us remembering. In a single package this would be a naming convention, and naming conventions lose. This is also why it is three packages rather than one: the API physically cannot import the pipeline.

  revix-api ──────┐
                  ├──> revix-core   models, settings, session
  revix-pipeline ─┘

The database mirrors the same idea

Four Postgres schemas separated by lifecycle rather than by subject, so it is always obvious which layer a table belongs to and what is allowed to write to it.

SchemaHoldsWritten by
rawFetched payloads, content-hashedIngest
coreCatalogue, sources, evidence unitsIngest and resolution
analysisAspect scores, evaluation runsEnrichment and fusion
servingFinished verdicts, claims, citationsFusion; read by the API

Schema changes are checked three ways

  • The migrations apply from empty.
  • They match the models, so editing a model without a migration is a red build.
  • They reverse cleanly, which is the one most projects never test.
Section 1, continued

The pipeline, stage by stage

Five stages, each a separate command, each runnable and debuggable on its own. The nightly simply runs them in order.

Ingest

Fetch from each source, politely. Store the response, deduplicate by hash

Extract

Split into sentences, find the topic and the polarity of each

Resolve

Decide which vehicle a listing is about, or refuse and queue it

Fuse

Weight, score, bootstrap the interval, apply the evidence floor

Publish

Write verdicts, claims and citations into the serving schema

What each stage guarantees

StageThe property it holdsWhy it matters
Ingest Idempotent, and isolated per source Re-running costs a hash lookup, not a duplicate. One dead source never stops the others
Extract Deterministic, no model call The same sentence always yields the same topic, so a verdict can be reproduced
Resolve Refuses below its confidence floor An unsure match becomes a queued decision for a person, never a guess in the data
Fuse Writes citations before prose exists The score is computed from the cited rows, so a citation cannot be wrong
Publish One row per variant per weighting Switching weighting on the site is a lookup, never a recomputation
Politeness is built in, not bolted on

Every outbound request passes a rate limiter, a robots.txt check and a circuit breaker that stops asking after repeated refusals. Three sources are read because three permit it: Team-BHP returns 403 to our agent and two others disallow us outright. We respect that rather than spoof a browser.

Frameworks, with justification

The artefact for this mark is the decision-record folder: nine ADRs, each stating the decision, the alternatives considered, and the consequence we accepted.

ChoiceWhy this oneWhat we did not do
FastAPI Contract-first. The TypeScript client is generated from the OpenAPI schema, so the two cannot drift Flask, and hand-syncing the client
Pydantic v2 Validation at the boundary, so a malformed request never reaches a query Manual checks scattered through handlers
SQLAlchemy 2.0 Typed ORM with bound parameters everywhere, so injection has no surface Raw SQL: quicker to write, impossible to refactor safely

The thread running through all of them

Each of these was chosen so that a mistake becomes a failed build rather than a defect a reader finds. The generated client, the typed ORM, the migration checks and the contract-first schema are all the same move: make the wrong thing impossible to merge rather than rely on noticing it.

Section 2, continued

The two choices worth arguing about

ADR 0002 · orchestration

Scheduled GitHub Actions instead of Airflow or Prefect. An orchestrator is a server to run, secure and pay for. Our pipeline is one nightly batch: no fan-out, no backfill, no dynamic DAG. Actions already holds our secrets, already runs on a schedule, and already gives us logs and alerting.

Choosing Airflow here would have been choosing a tool because it looks professional rather than because the problem needs it. If we ever needed backfill or fan-out, that ADR is where the decision gets revisited.

ADR 0004 · machine learning, and the honest result

We built a distant-supervision aspect classifier: lexicon labels train a TF-IDF into a one-vs-rest logistic regression.

It lost to the lexicon it learned from, so it ships disabled rather than being switched on because we had built it.

The comparison is a harness we can re-run, and /metrics publishes whatever has been recorded. Nothing is recorded there yet, because the hand-labelled gold set that makes the number defensible is the piece of work still outstanding. Quoting a figure we cannot reproduce on request would be the same mistake as shipping the model.

The measurement changed the code

The only E grade in the codebase

One function scored E (33), forty percent worse than the next worst block. Reading it, the cause was plain: _evaluate drew samples from the corpus and turned those observations into summary statistics. Neither half is complicated. Doing both in one place was.

Split along that seam into five functions — _draw, _score_one_draw, _rank_correlation, _calibration and _summarise — with a small value object carrying observations between the two halves. The thirteen tests covering it passed unchanged throughout, which is the only reason a refactor there was safe to make.

Method, not luck

Measure, find the worst thing, understand why it is the worst thing, fix the one that is safe to fix, and document the ones that are not.

BlockWhy the complexity is the domain's, not a style accident

The tool we left out, and what answers it instead

Five tools were used. The sixth was considered and rejected, which is worth stating rather than leaving as a silent omission.

Mutation testing

Mutmut changes your code on purpose and asks whether any test notices, which measures something no other tool here does: not whether tests exist, but whether they would catch a bug.

It has no native Windows support, and all three of us develop on Windows. A quality tool only one environment can run is one that stops being run.

Non-functional requirements

All nine categories audited against the actual code rather than against what the proposal claimed. Six were already satisfied by a single architectural decision, and that decision is worth explaining before the list.

The write path and the read path are strictly separated

22–35 ms
Warm response, local
Against a 300 ms p95 target
96–247 ms
From India, deployed
Inside target including the network

That one decision delivers four requirements at once. Performance, because nothing on the read path grows with the corpus, since the corpus is not on the read path. Scalability, because going from twenty thousand review units to a hundred thousand changes how long the night takes and changes nothing about a request. Reliability, because a page cannot fail when a third-party model is down. And availability, because a demo depends on nothing remote.

All nine, and where each is met

1 · Performance met

22–35 ms warm, 96–247 ms from India against a 300 ms target. Gzip 9.3×, cache directives, and X-Response-Time-ms on every response so the claim is checkable from outside

2 · Scalability met

Pagination capped at 200, bounded connection pool, the expensive work batched overnight where nobody is waiting

3 · Portability met

Docker image 364 MB running as a non-root user, uv lockfile, configuration only through environment variables. Developed on Windows, built and tested on Linux

4 · Usability audited

WCAG 2.1 AA clean on all ten pages, axe-core enforced in CI. The palette was reworked once because contrast failed, and the audit is what caught it

5 · Compatibility met

The TypeScript client is generated from the live schema, so the frontend cannot drift from the API. Responsive layout, standards only

6 · Security met

CSP and HSTS, CORS allow-list, rate limiting, no raw SQL, no secrets in a public repo, read-only public API and an authenticated operations surface

7 · Reliability met

Sources degrade independently behind a circuit breaker, every database wait is bounded, and no traceback ever reaches a caller

8 · Maintainability met

Strict types, 308 tests, nine decision records, a generated client, and configuration in one place

9 · Availability stated honestly

A 503 health contract and a keep-warm schedule. One free-tier instance is resilient to its dependencies failing, not highly available

What the audit changed

Five real gaps found and closed: no security headers anywhere, unbounded database waits, no rate limiting, no compression or caching, and no request identity

Measured, not asserted

Section 4, continued

The finding worth leading with

A requirement we had written, tested, and still not met

Our /health endpoint is deliberately built to report an unreachable database as a 503 rather than a 500 with a stack trace. It was written that way on purpose. There is a test for it.

It could not actually do it. There was no connect timeout, so the driver sat on the operating system's TCP timeout while the hosting platform's health probe gave up first. A correct 503 became no answer at all — and a hang is worse than an error, because nothing downstream can react to it.

What led us there was our own test run hanging for four hundred seconds against a machine with no database. Every wait is now bounded. The lesson is the difference between writing a non-functional requirement and verifying one: we had the code, the intent and the test, and the requirement was still not met.

Two limits we state rather than hide

LimitWhy it is the right call at this size
The rate limiter is per instance and in memory It bounds what one instance absorbs rather than enforcing a global quota, which fits the actual risk: one scraper exhausting a connection pool, not a distributed attack. A global quota needs Redis, and adding a network dependency to the read path to protect the read path is a bad trade here.
A single free-tier instance is resilient, not highly available There is no redundancy and no failover; buying that means two instances and a load balancer. Our mitigations target the failure that actually threatens a demo, a cold start or a sleeping database, rather than the one that does not.

Both are the first things that would need replacing if Revix grew. Stating a limit before being asked reads as engineering judgement; being caught at it does not.
